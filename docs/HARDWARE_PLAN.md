# UGen300 integration: plan and device results

Stage I runs every model on the host CPU (Intel Core i7-10700). Stage II moves the two models, the detector and Qwen2-VL-2B (which also drafts), onto one ASUS UGen300 (Hailo-10H, 8 GB) and leaves decoding, the draft checks, review and export on the host. The device path has now run on a UGen300: on 2026-11-05 we compiled the detector v4 HEF with Dataflow Compiler 5.3.0 and ran the device code under HailoRT 5.3.2 on a Windows 11 host, with the module on USB. The device code in `src/tracebrief/hailo_backend.py`, `src/tracebrief/device_pipeline.py` and `scripts/hailo/` targets HailoRT <!-- fact: hailo.hailort -->5.3.x, the release ASUS supports for the UGen300 (on Python 3.10); its HailoRT calls were also checked against the 5.3, 5.4 and 5.5 Python API sources [S20]. Source IDs refer to [SOURCES.md](SOURCES.md); the device records are in [data/evaluation/stage2/device](../data/evaluation/stage2/device/README.md).

**Every device figure here was measured with the UGen300's USB-C source advertising 0.9 A, so HailoRT ran the module in reduced-performance mode.** Re-measure on a USB-C port that supplies 3 A before quoting any of them as the device's speed.

The published figures predicted about 6.7 s per visual check (1.02 s + about 40 output tokens ÷ 7.04 tokens/s). At 0.9 A one visual check takes 13–17 s. The visual check, not the detector, is the bottleneck, so it runs only on candidates.

## Phases: the detector and the VLM take turns

Two measurements decide how a job uses the device. In one process the VLM's token read holds the Python GIL (the HailoRT 5.3.2 genai binding does not release it), so a detector thread got <!-- fact: device.same_process_fps -->0.37–0.43 FPS while the VLM generated. And on a Windows host over USB a second process cannot open the device at all (`LIBUSB_ERROR_ACCESS`), so the detector cannot run beside the VLM in another process either. The two models therefore take turns, and a job on the device runs in phases instead of interleaving them:

- **One clip:** detection of the whole clip in batches of 8, with its evidence frames; then the visual check of every candidate; then every draft. The device switches model once, from the detector to the VLM (<!-- fact: device.clip_switches -->1 switch in the recorded job).
- **Never at once:** both models share one lock (`Turns` in `hailo_backend.py`), so a draft requested from the review page while a clip is detected waits for the detector's batch to finish, and no batch starts while the VLM generates. The tests drive a fake device that records when each model is active and fail on any overlap.

The job record names the running phase (`phase`) and times each one (`phases`: seconds, candidates, model switches), and the result keeps them as `schedule`. On the host CPU nothing changes: each candidate is checked and drafted in turn.

One cost remains: the review page's own requests share the server process with the VLM, so a job-status answer can take up to <!-- fact: device.poll_wait_s -->7.2 s while the VLM generates.

## Detector: ONNX to HEF

The Fast search checkpoint (`weights/yolox-s-warehouse-v4.onnx`, detector v4) and the Stage I one (`weights/yolox-tiny-warehouse.onnx`) are opset 11 with a single `raw_predictions` output `[1, 3549, 7]` (two classes, 416×416 input, BGR 0–255, top-left letterbox padded with 114). The Stage I model's operator mix matches the Model Zoo `yolox_tiny` ONNX, and detector v4 has the same operators and node names at a larger channel width, so the standard parse → optimize → compile route applies. `scripts/hailo/compile_yolox_hef.py` runs it with the Dataflow Compiler's `ClientRunner`:

1. Parse with explicit end nodes before the decode head (the nine `reg_preds`/`Sigmoid` outputs of the three strides); the Model Zoo YAML's node names do not exist in our export and its ImageNet normalization must not be applied to this non-legacy model. The script checks the parsed HAR's output layers against `nms_yolox_warehouse.json`. DFC 5.3.0 puts the regression head on the other conv of each stride than the Model Zoo order the file was copied from; both NMS files now follow the 5.3.0 parse, and a test checks them against it.
2. Add `nms_postprocess(..., meta_arch=yolox, engine=cpu)` with the Model Zoo YOLOX NMS config changed to two classes and the profile's frozen confidence (0.25 for detector v4). HailoRT then runs NMS on the host and returns per-class boxes normalized to 0–1.
3. Optimize at level 2 (`--optimization-level`, the default) with 1,024 calibration frames drawn only from the model's training data, in a seeded shuffle, then compile for `hailo10h`. A GPU is not required: without one the DFC falls back to level 0 only when no level is given, and an explicit level runs on the CPU. On our 6-core CPU allocation level 2 took 1 h 29 min of fine-tuning and 2 h 07 min in all; compilation settles on 5 contexts and a 13.4 MB HEF.
4. Accept the HEF only if pair precision and recall on the same nine scorable test runs stay within two points of the ONNX model and every one of the nine decode heads has an SNR of at least 10 dB between the full-precision and quantized emulators on held-out frames. The build we use, o2s, passed both (see above). Two level-0 builds passed too; one of them had calibrated on a single dataset because the frames were passed in sorted order, which the script now prevents.

**Rebuilding the HEF.** The HEF cannot be rebuilt from this repository alone, which is why `config/hailo-manifest.json` records no hash for it. Its calibration frames are training images from third-party datasets that we do not redistribute: NVIDIA's SDG warehouse runs, NVIDIA PhysicalAI-SmartSpaces, LOCO and keremberke/forklift-object-detection (licences: [data/evaluation/stage2/detector-v4/DATA_LICENSES.md](../data/evaluation/stage2/detector-v4/DATA_LICENSES.md)). The DFC and its outputs stay outside the repository under Hailo's licence. To rebuild: download the datasets, take the 1,024 calibration frames from the detector v4 training pools only (our draw: SDG 342, SmartSpaces 250, LOCO 334, keremberke 98) and 64 acceptance frames from the validation pools (every frame's source image and SHA-256, and the calibration order, are in [hef-o2s/calibration_frames.json](../data/evaluation/stage2/device/hef-o2s/calibration_frames.json)), letterbox them with `compact_vision.preprocess`, then run `compile_yolox_hef.py --calibration-dir … --eval-dir … --optimization-level 2` with DFC 5.3.0 (the default `--calibration-seed 20261105` gives our order). With the same images, `acceptance.json` reproduces our `calibration_order_sha256` and `calibration_content_sha256` (the order and each file's SHA-256). Expect a different HEF hash: repeat the acceptance comparison, record the new SHA-256 in a local manifest (`TRACEBRIEF_HAILO_MANIFEST`) and keep it with the calibration list and DFC version.

## Visual check and drafting on the device

`hailo_platform.genai.VLM(vdevice, hef)` takes 336×336 RGB frames. Hailo's chat example centre-crops images, which would cut off the person or the forklift in our pair crops, so we pad each crop to a square before resizing. The prompt and parser are the frozen look-v2 ones (`src/tracebrief/look_prompt.py`, checked byte for byte against `scripts/look_local.py`), with the system message Hailo recommends when a conversation leads with an image; decoding is greedy with seed 19. The same resident VLM then drafts the brief from text alone with the draft-v2 prompt; HailoRT has no grammar-constrained decoding, so the reply is parsed and the usual source checks fall back to the labeled template when it fails. The context is cleared before and after every crop and draft, so system messages are accepted and nothing carries over between candidates, and the token stream is left as soon as the reply holds a complete JSON object. The HEF (3.26 GB for release 5.3.0) is downloadable from Hailo's public resource server, one per HailoRT release. A draft takes 30–80 s at 0.9 A (the longest when it runs to its 320-token limit); a reply that is not valid JSON is replaced by the template. The device drafts have not been audited the way the Stage I CPU drafts were, and an early one cited an evidence ID that does not exist (the source checks replaced it with the template).

**Against the CPU path** ([look-agreement](../data/evaluation/stage2/device/look-agreement/README.md); the device runs Hailo's compiled Qwen2-VL-2B, a different quantisation from the CPU's GGUF, on a padded 336×336 frame). On the 148 Stage I test crops, the exact published files, the device gave <!-- fact: device.look_same_verdict -->144 of 148 the same verdict as the published CPU run, and every answer could be read. The four differences: one person on a forklift answered as no person, and the three routine crops where the detector had boxed a rack upright as a forklift, all confirmed by the device (the CPU flagged two; its third answer was unreadable). With the device's answers the Stage I measures become <!-- fact: device.look_tp_confirmed -->103 of 106 annotation-matched pairs confirmed, <!-- fact: device.look_fp_flagged -->1 of 7 unmatched pairs flagged and <!-- fact: device.look_agreement_both -->141 of 148 crops agreeing with the visual labels, against <!-- fact: look.tp_confirmed -->104 of 106, <!-- fact: look.fp_flagged -->1 of 7 and <!-- fact: look.agreement_both -->144 of 148 on the CPU. The device's descriptions are longer, and about half repeat the prompt's "powered industrial truck". In the first run 15 of the 148 answers went on after the closing brace of the JSON, some to the token limit; the VLM now leaves the token stream as soon as the reply holds a complete JSON object, which gave the same 148 answers in <!-- fact: device.look_seconds -->14.4 s per crop (median) and 20.3 s at the 95th percentile, against 14.9 s and 38.2 s before. For drafting, 20 candidates fixed in advance were drafted on both paths: <!-- fact: device.draft_accepted -->17 of 20 device drafts passed the source checks against 20 of 20 CPU drafts, at 41.9 s per device draft against about 12 s on four CPU threads. The three rejected device drafts were a repetition loop to the token limit, an invented evidence ID and numbers absent from the input; the accepted ones mostly left out the review questions draft-v2 asks for and often had a generic title, which the source checks do not catch. Two stricter device-only format hints, chosen by a rule fixed beforehand on half of the candidates, did worse (4 and 1 of 10 against 9 of 10), so the device keeps the draft-v2-device hint. Drafting on the host CPU remains the more reliable choice at this power.

**A separate draft model was tried and rejected** ([draft-llm](../data/evaluation/stage2/device/draft-llm/README.md)). Hailo compiles the CPU path's own draft model, Qwen2.5-1.5B-Instruct, for HailoRT 5.3.0, so the draft phase could release the VLM, load that LLM on the same VDevice, draft and swap back. A rule written before its first draft required at least 8 of the 10 held-out candidates to pass the source checks (the VLM's result), a faster median draft and a swap that pays for itself within a draft phase of nine drafts. It met none of these: <!-- fact: device.llm_draft_accepted -->0 of 20 drafts passed (0 of 10 held out), because it wrote the review questions under `reviewQuestions` or as objects with answers, or looped to the token limit, and the two stricter hints did no better. It wrote indented JSON at the VLM's speed per token, so it took longer: <!-- fact: device.llm_draft_seconds -->52.7 s per draft (median) at 4.11 tokens/s, against the VLM's 41.9 s. Swapping to it took <!-- fact: device.llm_swap -->8.1 s (VLM released, LLM loaded), but loading the VLM again after the LLM failed in 7 of 7 recorded swaps back: HailoRT lost the device while it sent the VLM HEF and the UGen300 re-enumerated on USB, which ends the process's VDevice. It failed with or without the detector, with or without a draft and after a 10 s pause; released and loaded again with no LLM in between, the VLM loaded (13.6 s). Whether this is the 0.9 A supply or HailoRT 5.3.2 is open. So the device keeps drafting with the resident VLM and never swaps models in a job; `HailoLLM` stays in `hailo_backend.py` only to reproduce those records.

One process, one VDevice: with `TRACEBRIEF_BACKEND=hailo` the server opens a single VDevice with the ROUND_ROBIN scheduler, loads the detector and the VLM on it once, keeps both resident and releases them on shutdown. `genai.VLM` takes an existing VDevice, and Hailo's own voice-to-action demo runs an InferModel and GenAI models on one VDevice in one process [S20]. We set group `SHARED`, as Hailo's apps do, but on a Windows host over USB a second process cannot join the device whatever its group: HailoRT answers `HAILO_LIBUSB_FAILURE` (98) after libusb's `LIBUSB_ERROR_ACCESS`. TraceBrief turns that into a `DeviceError` that names the cause and what to stop (another TraceBrief server, the benchmark, `hailortcli`) in <!-- fact: device.held_s -->0.29 s, before any HEF is hashed; a job fails with that message. Before loading, every HEF is hashed against the manifest and the HailoRT release is checked; a missing device, a missing HailoRT or a mismatch fails the job with the reason, and no step falls back to the CPU.

## Interface choice: USB

We requested the USB version. It plugs into the PC that already stores the NVR exports without opening the case, which is the installation IT departments approve most easily. Our demand is well inside the USB throughput users report, and the visual check is compute-bound, not bandwidth-bound. Conditions to hold to: a direct USB-C 10 Gbps port able to supply 3 A, the supplied cable, no hub, firmware updated before testing, and a 12-hour thermal soak (users report shutdowns in long runs inside the stock enclosure) [S19]. Our measurements so far used a USB-A to USB-C cable on a port that advertised 0.9 A, which HailoRT flags as reduced-performance mode; that is the first thing to change. Also on this host: right after batch-8 jobs, `shutdown()` sometimes timed out and reset the device, so the detector now waits one second after its last job before it shuts down (it does so only at server exit); whether this is a power effect is still open.
